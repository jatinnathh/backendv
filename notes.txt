    ## Types of Authentication :  stateful , stateless , API key , OAuth 2.0
    
    # 1. Stateful Authentication
    
    In **stateful authentication**, the **server stores session information** about the logged-in user.
    
    After login:
    
    - Server creates a **session**
    - Session data is stored on the server
    - Client receives a **session ID**
    - Client sends session ID on every request
    
    ---
    
    ## Flow
    
    ```
    User logs in
       ↓
    Server verifies credentials
       ↓
    Server creates session in memory/database
       ↓
    Server sends Session ID cookie
       ↓
    Browser sends cookie on every request
       ↓
    Server checks session storage
    ```
    
    ---
    
    ## Example
    
    Traditional websites using:
    
    - PHP sessions
    - Express sessions
    - Django sessions
    
    ---
    
    ## Cookie Example
    
    ```
    Set-Cookie: sessionId=abc123
    ```
    
    Browser automatically sends:
    
    ```
    Cookie: sessionId=abc123
    ```
    
    ---
    
    ## Advantages
    
    - Easy to revoke sessions
    - More control on server
    - Good security for web apps
    
    ---
    
    ## Disadvantages
    
    - Server must store session data
    - Harder to scale horizontally
    - Requires shared session storage (Redis, DB)
    
    ---
    
    ## Common Technologies
    
    - Cookies
    - Session IDs
    - Redis session store
    
    ---
    
    # 2. Stateless Authentication
    
    In **stateless authentication**, the server does **NOT store session data**.
    
    Instead:
    
    - Client stores authentication token
    - Token contains user information
    - Server validates token on every request
    
    Usually done using:
    
    - JWT (JSON Web Token)
    
    ---
    
    ## Flow
    
    ```
    User logs in
       ↓
    Server generates JWT
       ↓
    Client stores JWT
       ↓
    Client sends JWT in Authorization header
       ↓
    Server validates signature
    ```
    
    ---
    
    ## Example Header
    
    ```
    Authorization: Bearer eyJhbGciOiJIUzI1Ni...
    ```
    
    ---
    
    ## JWT Structure
    
    A JWT has 3 parts:
    
    ```
    header.payload.signature
    ```
    
    Example:
    
    ```
    eyJhbGciOi...
    ```
    
    ---
    
    ## Advantages
    
    - No session storage needed
    - Easy horizontal scaling
    - Great for APIs and mobile apps
    
    ---
    
    ## Disadvantages
    
    - Harder to revoke tokens
    - Larger request size
    - Token theft risk if stored poorly
    
    ---
    
    ## Common Uses
    
    - REST APIs
    - Mobile apps
    - Microservices
    
    ---
    
    # Stateful vs Stateless
    
    | Feature | Stateful | Stateless |
    | --- | --- | --- |
    | Server stores session | Yes | No |
    | Uses cookies | Usually | Optional |
    | Scalable | Harder | Easier |
    | Revoking access | Easy | Harder |
    | Common token | Session ID | JWT |
    | Best for | Traditional web apps | APIs/mobile |
    
    ---
    
    # 3. API Key Authentication
    
    API key authentication is mainly used for:
    
    - Server-to-server communication
    - Public APIs
    - Developer APIs
    
    Client sends a unique API key with requests.
    
    ---
    
    ## Example
    
    ```
    x-api-key: 123456abcdef
    ```
    
    or
    
    ```
    Authorization: ApiKey 123456abcdef
    ```
    
    ---
    
    ## Flow
    
    ```
    Client sends API key
       ↓
    Server checks key in database
       ↓
    Access granted or denied
    ```
    
    ---
    
    ## Advantages
    
    - Very simple
    - Easy to implement
    - Good for machine access
    
    ---
    
    ## Disadvantages
    
    - Usually identifies application, not user
    - Weak security alone
    - Keys can be leaked
    
    ---
    
    ## Common Uses
    
    - Weather APIs
    - Payment gateways
    - Internal services
    
    ---
    
    # 4. OAuth 2.0
    
    OAuth 2.0 is an **authorization framework**.
    
    Important distinction:
    
    - Authentication = "Who are you?"
    - Authorization = "What can you access?"
    
    OAuth allows users to:
    
    > Grant limited access to another application without sharing passwords.
    > 
    
    OAuth 1.0 workflow below : 
    
    Shares tokens : a token has a limited access to your account on a platform 
    
    eg: token has only ability to read my contacts
    
    resource owner , client , resources server , authorization server 
    
    problem aith Oauth 1.0 → complex to implement , and crpytographic singatures (error prone )
    
    Oauth 2.0 introduced bearer tokens,  allowed developers to choose flows absed on the app type.                          
    
    ## Example
    
    "Login with Google"
    
    Instead of giving password to another app:
    
    - Google authenticates user
    - Google gives access token
    - App uses token
    
    ---
    
    ## Real Example
    
    You use a website:
    
    ```
    "Continue with Google"
    ```
    
    Flow:
    
    ```
    User clicks Google login
       ↓
    Redirected to Google
       ↓
    Google authenticates user
       ↓
    Google asks for permissions
       ↓
    Google sends authorization code
       ↓
    App exchanges code for access token
    ```
    
    ---
    
    ## Main OAuth Components
    
    | Component | Meaning |
    | --- | --- |
    | Resource Owner | User |
    | Client | Application |
    | Authorization Server | Google/GitHub |
    | Resource Server | API server |
    | Access Token | Temporary credential |
    
    ---
    
    ## Common OAuth Tokens
    
    ### Access Token
    
    Used to access APIs.
    
    ```
    Authorization: Bearer access_token
    ```
    
    ---
    
    ### Refresh Token
    
    Used to generate new access tokens without logging in again.
    
    Delegation → providing password of one platform to another platform 
    
    Open Id Connect → build on OAuth2.0
    
    Idtoken was introduced (Basically JWT) , had info like userid , Issue AT (Login time ) , issued authority 
    
    What to use when :
    
    Stateful : Web aps (SAAS based apps)
    
    Stateless : ideal for API or scalable systems 
    
    OAuth : third party integration 
    
    API key based : Server to server
